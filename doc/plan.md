## 第一轮：先补业务 Demo

默认下一课做评论，让已有视频可以被用户讨论。每课完成一条可运行的业务链，不要求一次完成表中整行。下列顺序可随用户反馈调整。

| 顺序 | 业务目标 | 基础验收 |
| --- | --- | --- |
| 1：新的第十课起 | 评论 | 登录用户给现有视频发评论，游客分页看评论，随后增加删除本人评论 |
| 2 | 关注与关注流 | 关注/取消关注作者，查看关注作者发布的视频 |
| 3 | 作者内容管理 | 查看自己的视频，修改标题、删除自己的视频并处理关联数据 |
| 4 | 话题与基础热榜 | 关联话题、按话题浏览；以清晰的 SQL 排序规则列出热门视频 |
| 5 | 互动通知 | 点赞、评论或关注后同步保存通知；收件人查询并标记已读 |
| 6 | 基础私信 | 发送文字消息，查看本人参与的会话及消息记录 |
| 7 | 简单真实上传与观看 | 业务功能齐备后再补本地文件上传并接入发布，届时重新设计，不恢复原第十一、十二课的整套方案 |
| 8 | Demo 整体验收 | 两个账号走通发布、浏览、互动、关注和消息，列出下一轮要解决的问题 |

短期复用当前 title + playback_url 发布方式，使用已知可访问的视频地址，不把文件生命周期设计放在评论、关注之前。真实上传本身也是业务功能，并非准生产专属；此次按用户要求移除旧实现，调整实现时机和规模。

继续使用 Gin、Gorm、SQLite。字段约束、身份与所有权检查、必要事务随当前业务实现；限制和缺点如实记下，但不为了未来可能出现的问题提前堆功能。

## 第二轮：围绕已完成业务学习组件与改进

Redis、RabbitMQ、Worker 保留在学习范围里。先有能工作的简单业务，再解释为什么值得改造。

| 方向 | 从已有业务出发 |
| --- | --- |
| Redis | SQL 热榜改为有序集合；详情读取引入缓存，再学习 TTL、失效和重建 |
| RabbitMQ 与 Worker | 同步通知改为异步处理，观察生产、积压、消费、确认与失败重试 |
| 媒体处理 | 自动封面、文件探测等有明确需求时引入，先同步跑通再考虑后台任务 |
| 数据库与存储 | 根据运行和学习需要迁移 MySQL、使用版本化迁移或对象存储 |
| 工程迭代 | 有具体问题后逐步处理请求限制、会话、日志、部署、幂等、故障恢复与测量 |

这些方向不是第一轮 Demo 的完成条件。不要把它们预先排成必须先完成的“准生产基线”。

## 教学与文档约定

助手设计、实现并验证，用户阅读代码、发请求、观察数据和提问；每个新增函数前写一句中文业务作用注释。每轮默认一条有业务意义的调用链，用户明确要求多课时再按授权调整规模。

笔记先把业务过程和代码结合：谁发请求、携带什么、进入哪个文件的哪个函数、调用谁、结果返回哪里。新概念先用脱离项目的最小例子解释。新增结构体、字段和表按“业务要记录什么 → 关系 → 字段来源/类型/零值 → 约束与索引 → 模型和迁移 → Repository → Service → Handler → Router”展开。

提供可点击的相对文件链接、链接旁的准确行号、调用图、请求与数据库验证步骤。区分请求、数据库模型与响应；不能把业务关联说成已实现的数据库外键。练习从预测结果、找代码和修改一个字段开始。验证通过不代表用户已经理解，进度中分开记录。
