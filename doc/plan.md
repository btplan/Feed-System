## 第一轮：补齐业务功能

以下是实施顺序，不是要求每行一次写完。每课仍完成一条有业务意义、可运行的调用链。

| 顺序 | 新业务 | 可观察的结果 |
| --- | --- | --- |
| 1，已实现待用户验收 | 上传真实视频文件，先保存到本地 | 提交文件后能找到磁盘文件，通过返回的 HTTP 地址访问它；包含本步必要的类型、大小与路径检查 |
| 2，已实现待用户验收 | 把上传结果接入发布与观看 | 当前用户发布自己上传的视频；其他用户从列表和详情取得地址并观看 |
| 3 | 作者内容管理 | 查看自己的视频，修改标题或删除自己的视频；明确文件与记录的处理关系 |
| 4 | 评论 | 发布评论、分页查看、删除自己的评论 |
| 5 | 关注与关注流 | 关注/取消关注作者，查看关注作者的视频 |
| 6 | 话题与基础热榜 | 发布时关联话题，按话题浏览；先按明确的 SQL 排序规则查看热门视频 |
| 7 | 互动通知 | 点赞、评论、关注后同步保存通知；收件人查询并标记已读 |
| 8 | 基础私信 | 发送文字消息，查询自己参与的会话与历史消息 |
| 9 | Demo 整体验收 | 两个账号完整走通上传发布、观看互动、关注与消息链，记录剩余问题 |

当前继续使用 Gin、Gorm、SQLite 和本地文件存储。新功能需要的字段约束、身份与所有权检查、必要事务随功能实现，不为演示省略业务正确性；但不先铺开缓存、队列、对象存储和完整部署体系。

## 第二轮：在已完成的业务上学习组件并迭代

Redis、RabbitMQ、Worker 仍在学习范围内，不取消。先有可运行的同步业务，再比较改造前后的行为；以下是候选顺序，Demo 完成后结合问题调整。

| 迭代方向 | 对应已有业务与学习问题 |
| --- | --- |
| Redis 热榜与详情缓存 | 在已有 SQL 热榜、视频详情上学习有序集合、GET/SET/TTL、更新失效与数据重建 |
| RabbitMQ 与 Worker | 把已有同步通知改为异步生成；观察发送、积压、消费、确认、失败重试与重复消费 |
| 媒体处理 | 自动生成封面，先跑通处理，再放入后台任务，理解处理状态与失败结果 |
| MySQL 与迁移 | 在已有表和数据上学习数据库迁移、索引、事务差异与版本化变更 |
| 存储与账号体验 | 根据实际问题引入对象存储、令牌续期/退出、限流等改进 |
| 可靠性与运行 | 对已经使用的缓存和队列补故障恢复、幂等与必要的 Outbox；再完善日志、部署与测量 |

这些是后续学习方向，不是当前 Demo 的完成条件。工程改造要说明具体触发问题、收益和代价，不以组件数量或“准生产级”标签推动进度。

## 每课的教学与验收方式

助手设计、落代码并运行验证；用户按配套文档阅读、发请求、观察数据。每个新增函数前写一句业务作用注释。

先把业务过程与代码位置结合说明。引入新概念前给脱离项目的最小例子；需要新模型时按业务需求 → 字段来源与类型 → 约束和关系 → 结构体及数据库 → Repository → Service → Handler → Router 的构建顺序讲解。没有涉及的层不为形式而新增。

文档提供可点击的相对文件链接、明确行号、调用及返回位置、调用图、请求和数据验证步骤。练习从预测结果、定位代码和修改一个字段开始。当前课理解与验收后再推进下一课。

Demo 验收依据是上述业务能够串起来运行，不是吞吐、部署或可用性指标。发现的限制记录下来，作为后续迭代输入。
