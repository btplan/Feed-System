## 最终目标与教学原则

采用模块化单体 API + 独立后台 Worker；核心数据使用 MySQL，Redis 用于有明确用途的缓存、限流和热榜，RabbitMQ 传递异步事件，对象存储保存视频与封面。引入组件的依据是业务与运行要求，不以组件数量判断是否达到准生产级。

“循序渐进”表示把完整能力拆成可验收的课，不表示最终只保留演示功能。每个阶段必须记录：已实现、尚缺能力、当前限制、补齐阶段、验证证据。安全与数据正确性问题发现后及时修复，不能因“后面会讲”而宣称当前可公开上线。

当前没有流量、机器规格、响应时延目标等运行条件，不承诺并发数字或可用性百分比。容量阶段先确定测试环境和目标，再测吞吐、P95/P99 延迟、错误率与资源占用，记录适用边界。完成最终验收前，项目定位为逐步加固的开发版本。

每课仍先讲业务与独立最小例子，再讲实体关系、字段来源和类型、约束与索引、结构体、迁移、Repository、Service、Handler、Router。异步课先设计事件、生产者和消费者。笔记将业务步骤与可点击文件、行号、调用及返回位置结合，不能只贴代码让学习者消化。

以下是阶段而非固定课号；每个阶段按一条业务链拆成多课，不在一轮生成整套系统。原课号 0–8 保留，后续从第九课起沿此顺序推进。

| 阶段 | 业务与工程成果 | 关键验收 |
| --- | --- | --- |

| B MySQL 与迁移 | 开发环境 MySQL；版本化 SQL 迁移替代部署时 AutoMigrate；连接池；索引、关系完整性与删除策略；用户身份失效检查 | 空库和旧版本升级均可执行；MySQL 上集成测试、重复/并发点赞与事务失败测试；备份恢复演练；不破坏原学习库 |
| C 真实上传与发布 | 文件大小与内容校验；对象存储；上传凭证或受控上传接口；所有权检查；上传完成后发布；失败文件清理 | 能上传并播放真实文件；不能冒用他人文件；非法文件被拒绝；上传成功但发布失败可清理或恢复 |

| E Redis 详情缓存 | SET/GET/TTL 最小例子；详情缓存；失效策略、超时与数据库回退；热点并发读取保护 | 命中率与查询次数可观察；修改后按约定恢复新数据；Redis 故障不致整个读取服务不可用，回退压力有边界 |
| F Redis 限流与账号会话 | 登录及敏感接口限流；退出/撤销与令牌续期策略逐课设计 | 触发限制得到明确响应；退出后的凭证按约定失效；说明 Redis 故障时放行还是拒绝及其影响 |
| G 评论与关注 | 评论发布/分页/删除、关注关系及关注流；审视关联删除与权限 | 不越权、重复操作结果明确、分页与关联数据正确 |
| H 通知基本链 | 通知表与收件人权限，先同步生成并查询通知 | 点赞/评论与收件人关系正确，只有收件人能查自己的通知 |
| I RabbitMQ 与 Worker | 独立生产消费最小例子；通知异步化；持久化配置、发布确认、消费 Ack、重试与失败队列、事件 ID 幂等 | 停 Worker 可观察积压；恢复可消费；处理失败不提前 Ack；重复事件只生成一条通知 |
| J Outbox 可靠投递 | 同库事务写业务与待发事件；后台投递；重试、重复发送、重启恢复 | 模拟数据库提交后队列不可用；恢复后事件可补发；发送成功但标记失败引起重复时仍安全 |
| K 媒体后台处理 | 封面/转码任务逐课引入；状态机；超时、重试、资源限制；发布可见性 | 上传与处理状态可查询；处理失败不会伪装成可播放；任务重启可恢复，重复任务不会破坏结果 |
| L 热榜与缓存扩展 | Redis 有序集合、评分规则、事件驱动更新和重建；按测量结果选择首页、计数等缓存 | 排名可解释；重复事件不重复累计；Redis 派生数据丢失可恢复；明确允许的数据延迟 |
| M 部署与运行验收 | Docker Compose/镜像、环境隔离、健康与就绪检查、优雅退出、结构化日志、指标告警、CI、运行手册 | 干净环境可启动；API/Worker 可平滑停止；数据库、Redis、队列故障可定位；负载与恢复测试有报告 |

环境操作随组件首次出现就讲，不等到 M 才讲如何启动 MySQL 或 RabbitMQ。M 负责整合与验证。版本化迁移、真实 MySQL 测试和故障测试是必做项，不能只留在文档里。

SSE 实时通知和私信是后续独立业务扩展。分片上传、复杂推荐、多级缓存和微服务拆分由实际需求决定，不作为准生产级的形式要求。前端仍暂不搭建。

## Redis、消息队列具体用在哪里

- Redis 详情缓存：减少相同视频的重复查库；必须同时考虑过期、更新后失效、缓存故障和热点压力。
- Redis 限流与会话状态：限制滥用请求，在业务要求退出或撤销时保存必要状态，不能把它误当成 JWT 签名验证本身的必需依赖。
- Redis 热榜：维护排序与分数；正式数据与事件足以支持重建。点赞计数和首页缓存按测试结果再引入，不预设所有读取都经过 Redis。
- RabbitMQ：传递通知、媒体处理等异步任务；不是点赞关系的唯一存储。
- Worker：独立 Go 进程，接收任务、执行并确认；处理失败要有重试上限和可观察的失败结果。
- MySQL：保存账号、视频、互动、通知与待发事件等正式记录。缓存可丢并重建，正式记录必须考虑持久性、备份和恢复。

异步链目标：业务数据与 Outbox 事件同库提交 → 返回业务成功 → 后台发布 RabbitMQ → Worker 写通知或处理媒体 → 成功确认。设计接受可能重复投递，通过幂等避免重复业务副作用，不承诺消息天然只到一次。

## 准生产级完成标准

1. 核心业务可端到端运行，输入、身份、所有权和错误语义有测试覆盖；真实文件能上传和播放。
2. 核心数据由 MySQL 约束与事务保护，版本化迁移和恢复流程验证过；关键并发行为在目标数据库上测试。
3. 缓存失效、降级、队列重复与丢失风险、Worker 失败和重启恢复都有明确策略及故障演练证据。
4. 开发/测试/部署配置分离，凭据不写死；日志可定位问题且不泄露敏感信息；请求和后台任务具备超时及资源边界。
5. 自动测试、构建、部署说明、备份恢复、指标告警和明确环境下的负载测试报告齐备。
6. 未完成的功能与风险明确披露，不能把“本地一次请求成功”当作已达到部署标准。真实上线另行结合实际环境验收。
